## What worked

- The site raised the alert by itself with the dispatch token, and the engine ran on `repository_dispatch` with no human involved.
- One failed tick did **not** raise an incident (anti-flap rule).
- The game day was tagged end to end: `(game day: github_5xx)` in the alert text, and `fault` on the ledger events.
- Recovery evidence arrived automatically, and resolving stayed a human decision.
- Server-side SLO cost: 2 failed ticker runs out of 86 allowed per 30 days.

## What broke or surprised (findings)

1. **A manual test incident swallowed the real alert.** Dedupe matched on service only, so the open Grok-key test #2 absorbed the game-day alert. **Fixed** in the engine (engine `4fb369f`): dedupe on monitor **and** service, with a test.
2. **The dashboard said "Operating normally" while the job was failing.** "Right now" only checks snapshot freshness (< 30 min), so for ~20 minutes an operator would have seen green. **Fixed** (ADR-017): "Right now" shows *Degraded: last scheduled run failed* with the reason while the snapshot is still fresh.
3. **Two failed ticks always reach the staleness edge.** Last good 05:10:15 and next good 05:40:15 is a gap of exactly 30:00, the same as the threshold (`STALE_AFTER_S = 1800`), so the page flipped to "Heartbeat late" for ~15 s, and a probe in that window would page. **Fixed** (ADR-017): staleness limit raised to 35 min. UptimeRobot did **not** page: the 15-second window fell between two 5-minute probes, so this was a near miss decided by timing.
4. **The agent's own detection gaps (from Grok on #2):** vikrantsingh.fyi has no CMDB entry (no owner or blast radius), and there's no runbook link for "GitHub 503 = external dependency". **Fixed** in the engine CMDB: `vikrantsingh.fyi` → `site-heartbeat` → `github-api` and `cloudflare-kv`, with owner teams and a runbook hint.

5. **Closing the issue with GitHub's button bypassed the agent.** At 05:47 `/resolve` from TRIAGING was **refused by the lifecycle (the gate held)**, but the same click closed the issue, so GitHub said closed while the record said TRIAGING. **Fixed** in the engine (engine `4fb369f`): `incident-guard` reopens an incident issue closed by hand unless the record is CLOSED, refusals now name the valid next step, and `/ack` takes only the steps still needed.
6. **A leading space made a command silently disappear.** `" /ack"` failed the workflow filter (`startsWith '/'`), so the run was *skipped* with no reply. **Fixed** (engine `4fb369f`): the filter passes any owner comment containing `/`; the bridge trims, decides, and stays silent on non-commands. Lesson: a strict gate must never fail silently.

7. **The alert channel is nearly full.** Alerts go to an Outlook mailbox at 98% capacity, which warns it will stop receiving mail when full, so the pager would go silent. Owner: Vikrant (clear space or add a second channel, e.g. UptimeRobot app push).
8. **This game day never exercised the pager.** Detection came from the site's own incident desk. The paging path (probe → DOWN email) was last proven by a real 503 at 02:50 ET the same morning. A later game day should run long enough to page on purpose.
